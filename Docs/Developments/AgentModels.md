# A/B 模型分级与调度

T 工作包的档位用于安排独立审查会话 B，D 阶段的档位用于安排开发会话 A。A 提出建议，维护者决定实际调度。

<a id="review-tier"></a>
## T 工作包交审时评估 B

A 完成 change 的实现和本地检查后，按本次待审版本的实际改动、直接消费者、失败后果和证据复核难度给出 X、Y 或 Z 建议。一个 change 覆盖多个 T 时，按这次交审范围内最难独立核验的关键合同定档。

| 档位 | 定档依据 |
|---|---|
| X | 最高难度。高后果失效需要跨合同推导或组合重放才能确认，例如 GPU 资源寿命与跨帧状态发布联动，或多个原生边界只能通过联合证据核验。 |
| Y | 较困难或繁琐。受影响的模块、数值边界或失败分支较多，可根据明确的合同和检查入口逐段核验。 |
| Z | 常规审查。改动和直接消费者边界清楚，可用定向阅读与回归证据覆盖主要风险。 |

A 在当前问题单填写建议档位和具体理由，交接时给出该档的建议模型。B 按维护者确认的调度记录实际档位、模型与推理级别，尚未确认的字段保留待确认。 [当前问题单](../CodeReview.md) · [模型映射](#model-mapping)

整改复核通常沿用首审的 B 调度。若整改扩大实际影响面，或 B 发现交接时未知的高风险合同，A 或 B 可提出升档建议。调整时记录原因，沿用同一问题单、CR 编号及已核实证据。各档均执行完整的独立审查、注释、整改复核与验收。归档前将建议与实际审查配置摘要随验收证据留在 change tasks。 [独立审查闭环](../../AGENTS.md#review-loop)

<a id="development-tier"></a>
## D 阶段归档后评估下一阶段的 A

当前 A 在本阶段出口验收并归档后，查看开发计划中的下一阶段、各 T 工作包和相关架构合同，综合判断任务间依赖、关键合同的实现风险和阶段验收的难度。

| 档位 | 定档依据 |
|---|---|
| M | 困难复杂。多个 T 共同改动关键合同，或少数核心难点决定后续实现与阶段验收。例如跨模块状态事务与资源就绪联动，且需要贯通原生执行链验证。 |
| N | 常规开发。大多数 T 能沿现有模块和成熟实现推进，关键难点可局部解决，阶段验收可以按明确的合同组合已有检查和定向验证。 |

A 在下一阶段入口记录开发档位建议，并简述决定档位的 T 工作包及其依赖或风险。交接时一并给出映射模型，由维护者在下一阶段启动前决定调度。阶段范围发生实质变化时，当前 A 可重新评估并更新建议。 [开发计划](Developments.md#current-stage) · [模型映射](#model-mapping)
